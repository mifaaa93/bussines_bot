# ТЗ: Telegram-бот секретарь

Версия черновика: 0.1  
Статус: согласование, код не пишем, пока ТЗ не утверждено.

## 1. Цель

Личный бот-секретарь для Telegram Business.

Владелец подключает бота как секретаря бизнес-аккаунта. Бот молча складывает все сообщения из бизнес-чатов в свою базу. Когда собеседник (или владелец) **меняет** или **удаляет** сообщение, бот пишет об этом владельцу в личку с ботом — в нужный **топик**.

Позже тот же бот можно открыть друзьям: у каждого свой `/start`, своя личка с топиками, своё подключение секретаря. Схема это учитывает сразу, мультиаренда в v1 не обязательна.

Это **не** автоответчик и **не** зеркало всех входящих. В топики попадают только события «изменено» и «удалено». Полная история живёт в БД.

**Главное в уведомлении:** сразу видно, *какой это человек и какой чат*. Без кликабельной ссылки/айди событие бесполезно — фото из десяти диалогов не отличить.

## 2. Что уже проверено на живом API

Подключение: `@reply_secret_pro_bot` как секретарь.

| Событие | Апдейт | Что внутри |
|---|---|---|
| Новое сообщение | `business_message` | полный объект: текст, фото, `file_id`, чат, отправитель |
| Правка | `edited_business_message` | **только новая версия**. Старого текста нет |
| Удаление | `deleted_business_messages` | `chat` + список `message_id`. Текста и медиа нет |
| Обычное фото | `business_message.photo` | `getFile` + скачивание работают (лимит Bot API ~20 МБ) |
| Одноразовое / self-destruct фото | — | **апдейт не приходит вообще** |

Следствия, которые нельзя обойти:

1. Старый текст при правке берём **только из своей БД**.
2. Содержимое при удалении берём **только из своей БД**.
3. Если бот был выключен и сообщение не записали — при удалении/правке честно пишем «содержимое неизвестно».
4. Одноразовые фото/видео секретарю недоступны. В v1 не обещаем их сохранять.

## 3. Роли и чаты

- **Владелец** — пользователь, который написал боту `/start` и подключил его в Настройки → Telegram Business → Чат-боты.
- **Бизнес-чат** — только **личная переписка** (`chat.type == "private"`) на бизнес-аккаунте владельца. Группы, супергруппы и каналы секретарь **игнорирует**: не пишет в БД и не шлёт уведомления.
- **Админ-чат** — личка владельца с ботом. Здесь топики и уведомления. Сюда **не** пишем копии всех входящих.

v1: белый список `OWNER_USER_ID` в `.env`. Чужие `/start` игнорируем или отвечаем «бот личный».

Уведомления шлём в `user_chat_id` из `BusinessConnection` (это личка бота с владельцем бизнес-аккаунта). Он должен совпасть с владельцем после `/start`.

## 4. Топики в личке с ботом

Топики в private chat с ботом поддерживаются (Bot API 9.3+): `createForumTopic` + `message_thread_id`.

Нужно один раз:

1. В @BotFather включить threaded / forum mode для бота.
2. Владелец открывает личку с ботом и включает топики (если клиент спрашивает).
3. `/start` создаёт набор топиков и запоминает `message_thread_id` в БД.

Топики **плоские**, вложенности нет. Матрица: **событие × тип контента**.

### 4.1 События

- `deleted` — удалено
- `edited` — изменено

### 4.2 Типы контента (канонические)

Один основной тип на сообщение, приоритет сверху вниз, если вдруг несколько полей (так бывает редко):

| kind | Топик (суффикс) | Что сюда |
|---|---|---|
| `text` | Текст | только текст, без вложений |
| `photo` | Фото | сжатое фото, в т.ч. live photo как фото+видео если API отдаст photo |
| `video` | Видео | видео |
| `animation` | GIF | mpeg4 gif |
| `video_note` | Кружок | video note |
| `voice` | Голос | голосовые |
| `audio` | Аудио | музыка/файлы audio |
| `document` | Файлы | документы, фото «как файл» |
| `sticker` | Стикеры | обычные / video / tgs |
| `other` | Прочее | контакт, гео, опрос, дайс, story, gift, invoice, checklist, неизвестное |

Имена топиков:

- `Удалено · Текст`
- `Изменено · Текст`
- … и так для каждого kind.

Плюс служебный топик `Служебное`: онбординг, «не удалось отправить по file_id», «бот перезапущен», «секретарь отключён», «сообщение не было в базе».

Итого: 10 kind × 2 + 1 служебный = **21 топик**.

Если `createForumTopic` падает (топики не включены) — пишем в General одним сообщением инструкцию и **не теряем** события: кладём в очередь `pending_notifications` и ретраим после успешного создания топиков.

### 4.3 Альбомы (не отдельный тип)

Проверено на API: альбом — это **несколько** `business_message` с общим `media_group_id`. У каждого свой `message_id` и свой тип (`photo` / `video`).

- В БД каждый кадр — обычное сообщение. `media_group_id` храним как поле, на маршрутизацию не влияет.
- Правка кадра → `edited_business_message` на **этот** `message_id` → топик `Изменено · Фото` или `Изменено · Видео`.
- Удаление кадра или всего альбома → список id, каждый обрабатываем **отдельно** как удаление фото или видео.
- Отдельного топика «Альбомы» нет.

## 5. Поведение

### 5.0 Фильтр чатов (жёстко)

Первым делом смотрим `chat.type`.

- `private` — обрабатываем (БД + уведомления по правилам ниже).
- `group` / `supergroup` / `channel` — **стоп**: апдейт не пишем в `messages`, в топики ничего не шлём, даже в Служебное.
- Админ-чат с ботом — не бизнес-воронка.

То же для `edited_business_message` и `deleted_business_messages` (у удаления тип чата есть в `deleted.chat.type`).

### 5.1 Входящий `business_message`

0. Если чат не `private` — выйти.
1. Нормализовать и UPSERT в `messages` по ключу  
   `(business_connection_id, chat_id, message_id)`.
2. Записать снимок в `message_versions` (version=1).
3. Медиа на диск **не качаем**. Храним `file_id` / `file_unique_id` и метаданные.
4. В топики **ничего не писать**.

В БД пишем все **личные** business-сообщения (и чужие, и свои): иначе нет контекста reply и дырявая история. Группы/каналы не пишем.

**Уведомления только по чужим.** Свои исходящие, свои правки и свои удаления — в топики не дублируем, только обновляем БД.

Чужое = `from_user.id != connections.user_id` (владелец бизнес-аккаунта). Сообщения, которые бот отправил от имени аккаунта (`sender_business_bot`), считаем своими.

Служебные сообщения Telegram без `from_user` — kind=`other`, в топики не пишем, пока не станет ясно, что это чужой контент.

Сообщения из админ-чата с ботом в эту воронку **не** попадают.

### 5.2 `edited_business_message`

Правка бывает не только у текста. На живом тесте альбома собеседник **заменил само фото и само видео** — пришёл новый `file_id` / `file_unique_id`, `message_id` тот же.

Что сравниваем со снимком в БД:

- `text` / `caption` (описание под медиа)
- `file_unique_id` вложения (замена фото/видео/документа)
- `kind`, если тип сменился
- `entities`

Поведение:

0. Если чат не `private` — выйти.
1. Найти старую запись. Если нет — вставить текущую версию. Уведомление «изменено, предыдущая версия неизвестна» — только если чужое.
2. Если снимок эквивалентен — **молчать** (служебный edit без изменений).
3. Иначе сохранить новую версию. Уведомление в `Изменено · {kind}` **только если чужое**. Kind — по **новой** версии; если тип сменился, в шапке `было: photo → стало: video`.
4. В уведомлении явно сказать, *что* изменилось: подпись, медиа, или оба.

Формат медиа-правки — в 6.3.

### 5.3 `deleted_business_messages`

Один апдейт может нести **пачку** id.

0. Если `deleted.chat.type != "private"` — выйти, ничего не писать и не уведомлять.
1. Разложить id по записям БД. Каждый id — отдельное событие (кадр альбома не склеиваем).
2. Пометить `deleted_at`. Повторное удаление того же id — игнор.
3. Неизвестные id: одно уведомление в `Служебное` со списком id + чат (могли быть чужими, пока бот лежал).
4. Известные **свои** (from = владелец): только `deleted_at`, без топика.
5. Известные **чужие**: по одному уведомлению в `Удалено · {kind}` этого сообщения.
6. Пачка из >5 чужих текстовых в одном апдейте: **сводка** + файл `deleted_YYYYMMDD_HHMMSS.txt`, чтобы не зафлудить топик. Медиа в пачке всё равно шлём по одному (фото/видео по `file_id`).

### 5.4 `business_connection`

Сохраняем `id`, `user_id`, `user_chat_id`, `is_enabled`, `rights`.

- `is_enabled=false` — в Служебное: «секретарь отключён», запись апдейтов прекращается.
- Новый `connection_id` — старые сообщения остаются привязаны к старому id (история не смешивается).

## 6. Формат уведомлений

Пользовательский контент **никогда** не вставляем в HTML/Markdown без экранирования. v1: `parse_mode` только для нашей рамки, тело — в `<pre>` с экранированием `& < >`, либо отдельным сообщением без parse_mode, либо файлом.

### 6.1 Шапка: кто и какой чат (обязательно)

Каждое уведомление (текст, капшен к медиа, сводка) **всегда** несёт привязку к собеседнику. Это не опциональная строка, без неё уведомление не отправляем.

Откуда брать:

| Поле | Откуда |
|---|---|
| Чат | `chat` апдейта; при delete — из апдейта всегда есть `chat` |
| Отправитель | `from_user` сообщения; при delete его **нет** в апдейте — берём из БД по `(connection_id, chat_id, message_id)` |
| Нет записи в БД | чат из апдейта (id, имя, username), отправитель: «неизвестен, сообщения не было в базе» |

Как показывать, в таком порядке приоритета:

1. **Кликабельное имя** — `text_mention` (MessageEntity) на `from_user`. Работает даже без username, открывает карточку человека.
2. Если есть `username` — рядом `@username` и ссылка `https://t.me/username`.
3. **Всегда дублировать числовые id** текстом: `user_id=…`, `chat_id=…`. Ссылка может не открыться на части клиентов, id останется.
4. В личке чат и человек обычно совпадают — всё равно пишем имя и оба id.

Группы и каналы сюда не попадают (фильтр 5.0).

```
Удалено | Изменено
От: {кликабельное имя}  @username
user_id=480055341  chat_id=480055341
Когда: 2026-10-19 15:21 MSK
msg_id=22373
```

Капшен к фото/видео — **тот же блок** (лимит 1024). Если шапка + подпись не влезают: шапка приоритетнее, длинный старый текст уезжает во второе сообщение / файл. Имя и id обрезать нельзя.

`parse_mode` для шапки: HTML + экранирование имён, плюс entity `text_mention` на имя. Пользовательский текст сообщения в эту HTML-рамку не смешивать в сыром виде.

Для правки добавить `Было отправлено: …` и `Изменено: …`.

Если это reply и родитель есть в БД — строка `Ответ на: {обрезок 80 символов}`.

### 6.2 Лимит 4096 и большие тексты

Лимит `sendMessage` = 4096 символов. Капшен медиа = 1024.

Алгоритм для **текста/подписи** (правка — два тела: old и new):

1. Собрать шапку (~400 символов запас).
2. **Правка, оба тела короткие** (шапка + «Было» + «Стало» ≤ 3500): одно сообщение.
3. **Правка, каждое тело ≤ 3500, сумма нет**: два сообщения в том же топике, reply chain (второе — reply на первое).
4. **Иначе**: шапка «полный текст в файлах» + `bylo.txt` + `stalo.txt` (UTF-8). Для удаления — один `content.txt`.
5. Если оба текста > 500 символов, в шапке дополнительно **урезанный unified diff** (максимум 1200 символов, хвост `…`). Полные тексты всё равно файлами, если не влезли.

Никогда не режем середину слова молча: либо полное тело, либо файл.

### 6.3 Медиа в уведомлении

Цель: владелец **видит содержимое**, не только «было фото».

Порядок отправки:

1. Шлём медиа в топик **по `file_id`** (`sendPhoto` / `sendVideo` / `sendDocument` / …). Тот же бот, другой чат — так задумано Telegram.
2. Если Telegram ответил ошибкой (протух, forbidden, wrong type) — в том же топике текст: тип, размер, имя файла, `file_unique_id`. Без ретрая скачиванием.
3. Если `file_id` нет — «медиа было недоступно боту».

**Удаление:** обязательно отправить старое медиа по сохранённому `file_id` (в исходном чате его уже нет).

**Правка — три случая:**

| Что изменилось | Что слать |
|---|---|
| Только подпись (`file_unique_id` тот же) | текстовый diff подписи. Тяжёлое видео заново не дублируем |
| Только медиа (новый `file_unique_id`) | шапка «заменено фото/видео» + **было** (старый `file_id`) + **стало** (новый `file_id`) |
| И подпись, и медиа | diff подписи + оба файла (старый и новый) |

Стикеры: `sendSticker` по `file_id`. Протух — тип и emoji текстом.

### 6.4 Что не влезает в одно уведомление

Очередь исходящих: не более ~15 сообщений в минуту в один чат, уважать 429 Retry-After. События не теряем: таблица `outbox`.

## 7. Медиа: только `file_id`, без скачивания

На диск медиа **не сохраняем**. Каталога `data/media/` нет.

- В БД: `file_id` (для отправки), `file_unique_id`, размер, mime, имя, превью `file_id` если есть.
- Уведомление: `send*` с этим `file_id` в личку владельца / топик.
- `file_id` принадлежит боту и обычно живёт долго; гарантии «навсегда» нет. Протух — текстовая заглушка, без `getFile`/скачивания.
- Текстовые вложения `bylo.txt` / `stalo.txt` / сводки удалений — это **наши** сгенерированные файлы, не копии чужого медиа.

Проверка перед кодом: отправка фото по `file_id` из `business_message` в личку с ботом. Результат — в разделе 15.

## 8. Модель данных (SQLite)

Файл: `data/secretary.sqlite3`, WAL, `foreign_keys=ON`.

Хватит для одного владельца и нескольких друзей. Postgres не нужен в v1.

### owners

- `user_id` PK
- `admin_chat_id`
- `tz` default `Europe/Moscow`
- `created_at`

### topics

- `owner_user_id`
- `event` (`deleted` | `edited` | `system`)
- `kind` (канонический или `system`)
- `thread_id`
- UNIQUE(owner, event, kind)

### connections

- `connection_id` PK
- `owner_user_id`
- `user_chat_id`
- `is_enabled`
- `rights_json`
- `updated_at`

### messages

Ключ: `(connection_id, chat_id, message_id)`

- `date`, `edit_date`
- `from_user_id`, `from_json`
- `chat_json`
- `kind`
- `text`, `caption`
- `entities_json`
- `media_json` (file_id, unique_id, size, width/height/duration, mime, file_name)
- `media_group_id`
- `reply_to_message_id`
- `has_protected_content`
- `raw_json` — полный апдейт на случай новых полей
- `deleted_at` NULL
- `updated_at`

### message_versions

- `id` PK
- ключ сообщения
- `version` int
- `kind`, `text`, `caption`, `media_json`, `raw_json`
- `seen_at`

Нужно, чтобы показать «было → стало» даже после нескольких правок. В уведомлении сравниваем **последнюю известную** и новую. В БД копится история.

### outbox

- `id`
- `owner_user_id`
- `thread_id`
- `payload_json` (что отправить: текст, файлы, media group)
- `status` (`pending`, `sent`, `error`)
- `dedupe_key` UNIQUE — например  
  `edit:{conn}:{chat}:{msg_id}:{edit_date}`  
  `del:{conn}:{chat}:{msg_id}`
- `attempts`, `next_retry_at`

Дубликаты апдейтов (рестарт, повтор getUpdates) не должны слать второе «удалено».

### processed_updates

- `update_id` PK  
Страховка поверх outbox.

## 9. Гонки и баги, которые закрываем явно

| Ситуация | Поведение |
|---|---|
| Правка очень длинного текста | файлы `bylo.txt` / `stalo.txt`, без обрезки молча |
| Пользовательский `<b>` / `&` в тексте | экранирование, не ломаем parse_mode |
| Delete без from_user в апдейте | имя и user_id из БД; нет в БД — только chat из апдейта |
| Нет username | text_mention + user_id, без t.me-ссылки |
| Капшен 1024 | шапка с человеком не выкидывается, контент уезжает во второе сообщение |
| Бот лежал, сообщение не записано, потом delete/edit | «содержимое неизвестно», id+чат, топик Служебное или обычный с пометкой |
| Две правки подряд | два уведомления, каждое было=предыдущая версия |
| Edit без изменения текста/медиа | молчим |
| Повторный delete | молчим |
| Пачка delete 30 текстов | сводка + файл, не 30 постов |
| Удаление альбома (несколько id) | по уведомлению на каждый кадр, топик по kind кадра |
| Правка только caption | diff текста, медиа не дублируем |
| Правка замены фото/видео | шлём старый и новый `file_id` |
| `file_id` протух | текст-заглушка с метаданными, без скачивания |
| Одноразовое медиа | апдейта нет, в БД пусто |
| Топики не создались | outbox + инструкция в General |
| 429 от Telegram | Retry-After, outbox |
| Смена `business_connection_id` | новый ключ, старая история на месте |
| Рестарт посреди отправки | outbox: повтор по dedupe_key не создаёт второе уведомление |
| Сообщение из админ-чата | не пишем в messages бизнес-воронки |
| Группа / канал / супергруппа | игнор: ни БД, ни уведомление |
| Несколько фото sizes | храним и шлём **последний** (самый большой) |
| Caption + замена фото | kind=photo, и diff подписи, и оба файла |
| Голос/кружок | как медиафайлы |
| Неизвестный тип в будущем API | kind=other, raw_json сохраняем, в Прочее |

## 10. Онбординг

`/start` от владельца:

1. Создать/проверить топики.
2. Кратко объяснить: подключи секретаря, дальше молчу, пишу только про правки и удаления.
3. Если секретарь уже подключён — «связь есть, connection_id=…».

`/topics` — пересоздать отсутствующие топики (если владелец удалил ветку).

`/status` — бот жив, connection enabled, число сообщений в БД, очередь outbox.

Команды только в General / Служебное.

## 11. Стек v1

- SQLite + aiosqlite
- python-dotenv
- Логи: `logs/bot.log`
- Без вебхука, без веб-админки, без Docker (по желанию позже)

Polling выбран, потому что это личная машина и мы уже так тестировали. Offset не терять: подтверждать апдейт после успешной записи в БД и постановки в outbox.

## 12. Не входит в v1

- Ответы от имени бизнес-аккаунта
- Зеркало всех входящих в топики
- Одноразовые фото/видео (API не даёт)
- Поиск по истории из Telegram (только своя БД, поиск командой — можно v2)
- Мультиаккаунт друзей (схема готова, UI/whitelist расширим)
- Скачивание медиа на диск (шлём по `file_id`)
- Группы, супергруппы, каналы (секретарь только для личек)

## 13. Ключевые решения

1. **Пишем в топики только delete/edit**, всё подряд — в БД. Иначе личка превратится в помойку.
2. **Матрица топиков событие × тип**. Альбомы не выделяем: кадр = обычное фото или видео.
3. **Своя история версий**, потому что Telegram присылает только «стало».
4. **Outbox + dedupe**, чтобы рестарт и пачки delete не флудили.
5. **Большие тексты — файлами**, короткие — в сообщении. Никогда не резать содержимое без следа.
6. **Медиа не качаем**, в топики шлём по `file_id`. Протух — заглушка.
7. **Пользовательский текст не в сырой HTML**.
8. **Одноразовое медиа не обещаем.**
9. **v1 один владелец**, но `owner_user_id` везде в схеме.
10. **Уведомления только о чужих** сообщениях. Свои исходящие всё равно пишем в БД (контекст reply, история).
11. **Альбом = набор отдельных фото/видео.** Правка и удаление — по кадру, в топик Фото или Видео.
12. **Правка медиа** может быть подписью, заменой файла, или обоими. Смотрим `file_unique_id`.
13. **Общих лент «всё удалено / всё изменено» нет**, только нарезка по типам.
14. **В каждом уведомлении — кто и какой чат:** кликабельный `text_mention` + `@username` если есть + всегда `user_id` и `chat_id`. При delete отправитель только из БД.
15. **Только личные чаты.** Группы и каналы не сохраняем и не уведомляем.

## 14. План внедрения (после утверждения ТЗ)

1. Каркас: конфиг, SQLite, модели, `/start`.
2. Топики: создание, таблица `topics`, служебный топик.
3. Приём `business_message` (метаданные + `file_id`).
4. Outbox-воркер отправки в топики.
5. `edited_business_message` + формат «было/стало» + текстовые файлы при оверсайзе.
6. `deleted_business_messages` + отправка медиа по `file_id` (каждый id отдельно).
7. `business_connection`, `/status`, дыры «не было в базе».
8. Прогон сценариев из раздела 9.

## 15. Решения владельца (зафиксировано)

1. Уведомления **только по входящим от собеседников**. Свои правки/удаления в топики не пишем.
2. Альбомы **без своего топика**: каждый кадр — отдельное фото или видео (правка/удаление как у одиночного).
3. Только нарезка по типам, **без** общих лент.
4. Часовой пояс шапки: `Europe/Moscow`, пока не скажем иначе.
5. Медиа **не качаем**. В топики отправляем по `file_id`.
6. Правка фото/видео может заменить **сам файл**, не только подпись.
7. В уведомлении обязательно видно человека и чат (ссылка/mention + числовые id).
8. Только лички (`private`). Группы и каналы — полный игнор.
